Capital Control Engine

Optimal ≠ Safe.

The highest-return mathematical allocation is not automatically the allocation an institution should accept. CCE separates the two — and shows both.

The loop

Market data → Portfolio state → Risk engine → Detect → Optimize → Validate → Stress test → Explain → Human approval → Simulated rebalance → Audit → (repeat)

The optimizer is deliberately not the final authority. It generates candidate allocations; a separate control layer independently re-derives every metric and decides whether the candidate is acceptable.

What makes it different

Structural independence

The control engine cannot import the optimizer. That is enforced by a test that parses imports across the tree, not by convention. The validator recomputes every metric from raw returns rather than trusting the optimizer's own numbers — so a solver bug becomes a rejection, not an approval.

Risk contribution, not just weight

Allocation answers how much capital is here. Risk contribution answers how much of our risk is caused by this. Asked for the unconstrained optimum on real NSE data, the optimizer proposes gold at 31% of capital and 62% of portfolio risk. A weight-only framework waves that through.

On failure, do less

Any failure — optimizer, data, stress, database — preserves the Last Approved Safe Allocation. The system never invents one, and never relaxes a constraint to produce an answer.

The LLM writes prose, never decisions

Explanation only. It cannot touch a weight, a threshold, a risk score or an approval, and there is no path from its output back into decision state. The system runs fully with no API key.

Does the control layer actually help?

Walk-forward backtest, Sep 2024 – Aug 2026, monthly rebalance, identical data down both arms.

StrategyReturnVolatility Max drawdownPolicy breaches
Buy and hold12.8%8.7%8.8%0
Uncontrolled optimizer 33.5%11.3%6.5% 37
CCE-controlled 23.5% 7.3% 4.8% 0

The controlled strategy earned ten points less. We are not going to dress that up. In exchange: a third less volatility, a shallower drawdown, and zero policy breaches against thirty-seven. That is not outperformance — it is a different mandate, and saying so plainly is more credible than claiming otherwise on a single sample.

Every rebalance uses only data strictly before that date. The suite includes a test that injects a one-day look-ahead leak and fails if it goes undetected.

Twelve safety invariants — each with a test

  1. The LLM cannot modify financial decisions
  2. An invalid optimizer output cannot become an approved allocation
  3. A hard control failure cannot be silently ignored
  4. If optimization fails, retain the last approved allocation
  5. Missing critical market data is not zero risk
  6. Every approval and rejection is auditable
  7. Backtesting must not use future information
  8. Threshold changes are versioned and audited
  9. Current, optimal and safe allocations stay distinct
  10. A stress-test failure stays visible even if normal metrics pass
  11. Risk state is computed in exactly one place
  12. The UI contains no financial logic

571 tests pass, none skipped. Two invariants were deliberately left failing until the components they guard existed — a green tick against something never built is worse than a visible gap.

Built with

Python 3.11 · NumPy · pandas · SciPy · CVXPY · jugaad-data (NSE/RBI market data) · SQLite · Streamlit + Plotly · pytest, ruff, mypy.

Mean-variance optimization, EWMA volatility, historical VaR and CVaR, risk contribution, Rockafellar–Uryasev CVaR LP, Hierarchical Risk Parity, Black-Litterman, walk-forward backtesting.

Decision-support prototype. Not connected to any brokerage — approval triggers a simulated rebalance. Risk thresholds are configurable demonstration values, not Basel, SEBI or RBI limits. Expected returns are labelled “Model Estimate” everywhere they appear. No guarantee of returns is made or implied.
